description: When a domain type is shared between an error-payload diagnosis (parsed defensively in presentations/) and a success-response model (parsed via data/models Model.fromJson), put pure derivation logic (dedup, classification) in domain/helpers/ so both sides converge on identical business rules without importing across the presentations<->data boundary.

**Pattern:** LNS-692's `BlockingPosting` type is produced two ways: (1) a presentations-layer resolver (`close-period-error.ts`) defensively parses it out of a `ServerError.details` 422 payload — cannot import `data/models` per the layering rule; (2) a data-layer `BlockingPostingModel.fromJson()` parses the identical shape from a successful mutation response (`retry-failed-postings`). Both need the SAME derivation rules (which postings are "attributed and actionable", dedup accounts by id) so the diagnosis and the post-retry outcome render consistently.

**Solution:** Put the derivation as pure functions in `domain/helpers/` (e.g. `deriveBlockingOverheadAccounts(postings)`, `hasUnattributedBlockingPosting(postings)`) operating on the shared `domain/entities/` type. Both the presentations resolver AND the data Model's `toValue()`/`toEntity()` output converge on that one domain type, so the domain/helpers functions serve both call sites without either importing the other's layer. This is the same shape as `domain/helpers/price-tier-preview.ts` — CLAUDE.md's existing convention — but the two-producers-one-consumer angle (error path + success path needing identical business rules) is the non-obvious trigger for reaching for it.

**Why:** The BE contract explicitly called this out ("BlockingPosting element shape — shared by the 422 diagnosis AND the retry outcome — one type, one renderer serves both"), and duplicating the dedup/classification logic in two places (once in the presentations resolver, once wherever the retry outcome is rendered) would have been exactly the kind of drift CLAUDE.md's derived-invariant-getter rule warns against.

**The failure this prevents, which review caught here:** converging the *derivation* is not enough — converge the **parsing predicate** too. The first cut left two hand-rolled parsers for the same field, and they disagreed on malformed input: the presentations resolver returned `null` for an unusable `coa_account`, while `CoaAccountRefModel.fromJson` defaulted missing fields to `""` and never returned null. Same payload, opposite behaviour — on the success path it rendered a blank `" — "` label and wrongly ENABLED a remedy button that could not work. Fix: one `parseCoaAccountRef` in `domain/helpers/`, the Model delegating to it and returning `Model | null` rather than a default-filled instance, plus a test asserting both paths agree on the same malformed input. "Both parsers look correct" is not parity; assert it.

**How to apply:** When a brief says "shared by both X and Y" for a nested error-payload shape, check whether X is presentations-layer (defensive parsing, no data/models import) and Y is data-layer (Model.fromJson). If so, converge them on one `domain/entities/` type and put any derivation logic in `domain/helpers/`, not in either producer — and make the "is this field usable" predicate shared too, not just the derivation on top of it.
