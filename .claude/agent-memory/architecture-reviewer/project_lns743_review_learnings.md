Review of the LNS-743 cash-entry-settings page diff (2026-08-31) came back near-clean (one Minor). Things verified so future reviews don't re-litigate them:

- **The `details.code` unwrap in a `classify-*` helper is the validated template, not a smell.** `classifySaveError` does `err.code === ErrorCodes.UNKNOWN.code ? err.details?.code ?? err.code : err.code`. It holds because `HttpRequest` (unknown-code branch) passes `code: data.code` into details, and `ServerError`'s constructor does `Object.assign({}, {code: registryCode, ...}, details)` so the real BE code always wins in `details.code`. Extends the [[lns738-review-learnings]] `details.status`-not-`httpCode` rule: branch on the *unwrapped* code, never `httpCode`.
- **A page-level provider importing from its own `_components/` is established** (6 precedents: profitability, cash-entry-detail, journal-detail, recipe-edit, product-create, production-create). Not a layering violation.
- **`refresh: () => mutate()` typed as `KeyedMutator`** — confirmed again (see [[lns738-review-learnings]]): when the hook returns the raw `mutate`, `refresh?.().catch(() => {})` in a retry is correct, not an unguarded mutate.
- **`LedgerAccountCombobox` already calls `useListAllLedgerAccounts` itself**, so a page provider calling the same hook is the same SWR cache, not a provider-data-locality violation. Provider still needs its own copy to resolve saved-id→entity / detect a stale saved id.
- **One real Minor found**: `cash-entry-settings-error.tsx` offers "Coba lagi" unconditionally while the GET contract declares 403 (terminal) alongside 200 — its own comment asserts "every failure here is worth a retry", which the contract contradicts. Rule to reuse: the CLAUDE.md "omit the retry button when the error is terminal" carve-out is NOT_NOT_FOUND-only in the text; it generalizes to 403. Gate the retry on the error code.
- **Eligibility helper used as designed**: `cash-category-eligibility` doc comment says "narrow an account list before it reaches a picker, never to decide whether a request may be sent" — LNS-743 does exactly that (picker `filter` only, server-authoritative 422 rendered inline). A call site that instead *blocks* the request on the helper is the drift to flag.

Fix-commit delta review (2026-08-31, commit 4f97c0f5 — answered reviewer feedback "too many ifs in render" + "classify-fetch-error belongs in core"). Verified so future reviews don't re-litigate:

- **`classifyFetchError` now lives at `src/core/helpers/classify-fetch-error.ts`** (moved out of the page's `_utils/`). Its terminal set (FORBIDDEN + FEATURE_NOT_AVAILABLE), the `details.code` unwrap, and retryability semantics are unchanged by the move; the test even gained a case pinning that an *unregistered* BE code with `status: 403` stays retryable (terminal set is extended, never guessed from status). Update any citation of the old page path.
- **Resolver-extraction is the validated fix shape for "too many ifs in a component render"**: three pure `_utils/` resolvers (`resolve-account-field-state`, `resolve-settings-feedback`, `resolve-save-button-state`), each output consumed by a distinct DOM node, per-state presentation split into single-state components whose only conditional is an early `return null`. When reviewing such a refactor, verify (1) no stacked ternaries/`&&` chains resurrected in the .tsx, (2) every resolver output has a consumer (else it's a dumping ground), (3) the *baseline* shape actually had the sprawl (diff the old component first — the fix should be deleting real conditionals, not relocating them).
- **Cross-resolver invariant test bridge**: when a documented invariant spans two pure resolvers (here "button `disabled && !loading` is always paired with a feedback message"), one resolver's test file may import the sibling resolver and pin the pair — `resolve-save-button-state.test.ts` imports `resolveSettingsFeedback` for exactly this. Don't flag the cross-import as a coupling smell; it's the only place a spanning invariant can be regression-tested since each resolver alone can't express it.
- **`PlacedSaveError` hand-restating `Exclude<SaveErrorPlacement, "toast">` is compile-time-protected duplication, not drift-prone**: if `classify-save-error` ever adds a placement variant, assignment at the provider's `setSaveError` fails to compile. Restating a union is only dangerous when nothing re-checks it structurally.
- **Moving a page util to core requires de-page-coupling the doc comments**: the move correctly dropped "the GET contract declares only 200/403" and `CashEntryFeatureGate` page specifics, replacing them with the generalized rule ("per-endpoint terminal states like NOT_FOUND stay with the caller"). A moved file that still carries page-specific commentary is a smell the next consumer will trust wrongly.
