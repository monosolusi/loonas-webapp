description: A closed LoonasDialog IS unmounted from the DOM — the InternalDialog unmount=false default never applies because the wrapping Transition defaults unmount=true; verified against installed @headlessui/react 2.2.9
metadata:
  type: feedback
---

When reviewing any claim about what a closed `LoonasDialog` / Headless UI `Dialog` leaves in the DOM, do **not** accept "`unmount` defaults to `false`, so it stays mounted as `display:none`". That reads the wrong default. Verify the chain, not the one line.

**Why:** verified in the installed `@headlessui/react` 2.2.9 (`node_modules/@headlessui/react/dist/components/dialog/dialog.js` and `.../transition/transition.js`). `DialogFn` renders `<Transition show={open} transition={transition} unmount={rest.unmount}><InternalDialog/></Transition>`. `LoonasDialog` never forwards an `unmount` prop, so `rest.unmount === undefined`; `TransitionRoot` destructures `let {show, appear=false, unmount:S=!0, ...}` and `undefined` triggers the **`true`** default. It then renders with `features = RenderStrategy|Static` and `ourProps: {unmount: S}` → `RenderStrategy.Unmount` → returns `null`. `InternalDialog`'s own `unmount = false` default never gets a chance to apply, because the outer Transition already removed the subtree. Context7 (`/tailwindlabs/headlessui/_headlessui_react_v2_2_9`) quotes both defaults and it is easy to cite only the InternalDialog one and reach the opposite conclusion — a sibling agent did exactly that and wrote it into its own durable memory (LNS negative-stock guard, 2026-08-11).

**How to apply:** two consequences for review. (1) Worries about an *always-mounted* closed dialog — duplicate focus traps, a permanently-live `role="alert"` region, stale DOM form state — are moot; there is no DOM subtree while closed. (2) The mutually-exclusive-sibling-dialogs shape (`<><Blocked open={cond}/><Form open={!cond}/></>`) is still the right call, but for a different reason than usually stated: the Transition plays the leave animation on nested `TransitionChild`s (backdrop/panel carry `transition`) and unmounts only after, whereas an early return tears the `<Dialog>` down synchronously and the leave never plays. Approve the shape, correct the rationale. (3) **The leave window is real and is the one place a nullable item prop bites.** For ~200ms after `open` flips false (`data-leave:duration-200` on `LoonasDialog`'s backdrop and panel) the subtree is still mounted and re-renders with the props it has *now* — and the parent has usually already set `item = null` in the same click. So every `{item && …}` guard in the panel body blanks *visibly*, mid-fade. When an engineer justifies widening a shared helper to accept `null` "so the dialog doesn't blank during the fade", check the rest of the panel: if the name/amount/etc. still blank, the nullability is being absorbed in the wrong place. The fix is a last-non-null latch at the dialog boundary (fixes every field at once, keeps the shared helper's signature strict), not a nullable param on a helper that three call sites share and only one needs. Confirmed 2026-08-11 on `stock-adjustment-blocked-dialog.tsx`.

The latch shipped as `useLatchedValue<T>(value: T | null)` in `core/presentations/hooks/use-latched-value.ts` — **check it still exists before recommending it**, then point at it rather than re-deriving. Two details are load-bearing and worth checking in any reimplementation: it must return `value ?? latched` (not `latched` alone) so a newly-arrived item renders on the *same* pass instead of a frame late, and a `if (!latchedItem) return null` guard in the dialog body is safe *only* because the latch moves null→non-null once and never back, so a null result means the dialog has never opened and `open` is false anyway.

Related: [[css-hidden-dual-branch-singleton]] is the opposite case — CSS `hidden` really does keep both branches mounted.
