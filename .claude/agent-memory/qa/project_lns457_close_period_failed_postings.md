LNS-457 (branch `feat/lns-457-handle-period-has-failed-postings`, 2026-07-17): added distinct 422 handling for `PERIOD_HAS_FAILED_POSTINGS` on both `/finance/periods` and `/finance/fixed-costs` close-period dialogs, via shared helper `resolveClosePeriodErrorMessage` (`src/features/accounting/presentations/helpers/close-period-error.ts`) + shared `ClosePeriodEscalationHint` component. Full QA pass (typecheck/lint clean, browser smoke environmentally blocked per [[project_lns457_env_no_dotenv_clerk_keyless]]) — verified entirely via source-level tracing. Key facts for any future re-verification (e.g. post-LNS-456 BE ship, or a staging re-check):

- **Count guard**: `raw = err.details?.details?.failed_count; count = typeof raw === "number" && Number.isFinite(raw) && raw >= 1 ? raw : null`. Note the `>= 1` — `failed_count: 0` explicitly falls to the count-less fallback (not just non-number/undefined). This is deliberate and correct per AC-2 ("no '0'").
- **Nested details access** matches [[project_server_error_nested_details_access]] exactly — confirmed against `http-request.ts` L70-77 (registered-code path forwards `{ details: data.details }` into the `ServerError` ctor's `Object.assign`, landing at `err.details.details`).
- **Both providers' `handleClosePeriod` catch blocks are structurally identical**: `isFailedPostings` check → `setClosePeriodFailureCount(c => isFailedPostings ? c+1 : 0)` BEFORE the httpCode/code branching — meaning the counter resets to 0 on ANY non-failed-postings error (403, 409, other 422 codes, unknown), not just on success. Confirmed via full read of `periods-provider.tsx` L204-248 and `fixed-cost-entries-provider.tsx` L192-225.
- **No reason-wipe regression** (the LNS-377 defect class): `handleSubmit` in both dialogs only calls `setReason("")` when `handleClosePeriod` resolves `true` (success). On any failure the typed reason text survives untouched for retry — confirmed in both `close-period-dialog.tsx` and `fixed-cost-close-period-dialog.tsx`.
- **Idempotency key freshly minted per submit** (`crypto.randomUUID()` inside `handleClosePeriod`, called fresh on every invocation) — retry after a 422 is not blocked by a stale/cached idempotency key.
- **Consumer surface is exactly 2** (`grep -rn "resolveClosePeriodErrorMessage\|ClosePeriodEscalationHint"` across `src/`): the two target dialogs/providers, nothing else. No third close-period entry point was missed.
- **Fixed-costs provider had a real pre-existing bug this diff fixed as a side effect**: before this diff, `fixed-cost-entries-provider.tsx`'s 422 branch was `setClosePeriodError(err.message)` — leaking the raw BE message straight to the user for ANY 422 (not curated). After this diff it routes through the same `resolveClosePeriodErrorMessage` helper as `/finance/periods`. This is an improvement, not a regression — call it out positively in review.
- **`role="status" aria-live="polite" aria-atomic="false"` wrapper is single-instance per dialog file** (not a dual-CSS-layout duplicate per [[feedback_css_hidden_dual_branch_singleton]] concern) — each dialog has exactly one such div, unconditionally mounted, with `key={closePeriodFailureCount}` on the inner callout to force re-announcement of unchanged text across retries.
- **No jargon leak**: grepped `close-period-error.ts` + the new `ErrorCodes.PERIOD_HAS_FAILED_POSTINGS.message` for "dead-letter"/"outbox"/"posting" — none present. (Note: the PRE-EXISTING `PPH_FINAL_NOT_POSTED`/`PERIOD_NOT_DRAINED` messages DO use "diposting" — that's unrelated existing copy, out of scope, not a new jargon leak from this diff.)
- **`LOONAS_WHATSAPP_URL`** (`src/core/utilities/contact.ts`) is still `""` (TODO(LNS-344), pending PM/UID canonical link) — the escalation hint's WhatsApp button renders `disabled` by design, confirmed via `!LOONAS_WHATSAPP_URL` guard in `close-period-escalation-hint.tsx`.
- **AC-6 "unknown/unrelated 422" nuance**: the helper's fallback (any code that isn't the two named ones → `PERIOD_NOT_DRAINED.message`) only fires for codes that ARE registered in `ErrorCodes` with `httpCode: 422` (e.g. testing with `NORMAL_BALANCE_HINT`). A code the BE sends that is NOT registered in `ErrorCodes` at all gets rewrapped by `http-request.ts` as `ServerError(ErrorCodes.UNKNOWN)` (httpCode 500, not 422) — the provider's `err.httpCode === 422` branch never fires for that case, and the catch-all `else` branch shows a generic TOAST instead of the inline safe message. This is PRE-EXISTING behavior (not introduced by LNS-457) and the dialog still stays open either way (no branch calls dismiss on error) — worth flagging to EL as a nuance, not a defect.

**M1 fix-round delta (2026-07-17, same-day re-pass):** SWE extracted the inline `isFailedPostings` boolean expression into a named predicate `isPeriodHasFailedPostingsError(err: unknown): boolean` in `close-period-error.ts` (pure extraction — `err instanceof ServerError && err.httpCode === 422 && err.code === ErrorCodes.PERIOD_HAS_FAILED_POSTINGS.code`, byte-for-byte identical to the inline check it replaced). Both providers now call the helper instead of inlining the check; `resolveClosePeriodErrorMessage` is untouched; both dialogs are untouched; `server-error.ts` is untouched. Confirmed the ONLY two call sites of the new predicate are the two providers (`grep -rn "isPeriodHasFailedPostingsError" src/`). Re-ran tsc + lint clean.
